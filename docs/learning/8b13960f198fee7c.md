# Learning proposal: Allow CanvasKit WebGL in headless verifier

Status: proposed; human review and merge required.

## Observed problem

The shared Web verifier forced a CPU-only CanvasKit path that silently omitted Flutter image layers even though the assets loaded and rendered in a direct browser image.

## Proposed improvement

Use WebGL with SwiftShader in headless Chrome while retaining the existing screenshot, console, and soak gates.

Base commit: `77fe606beb3d63499d848fb8f762890ff21d4dfe`

## Source evidence

### joker-webgl-evidence.txt

SHA-256: `9a7618029f1484a54afa5c7c05b537b1bcd6a57e343e4a0459ac9798868a6d90`

    Observation: During Joker Jewels Chrome verification, the generated PNG files returned HTTP 200 and rendered in a direct browser <img>, but Flutter CanvasKit screenshots showed blank stage and symbol art when tools/web_verify.mjs launched Chrome with --disable-gpu.

    Reproduction: the CPU-only run logged "WARNING: Falling back to CPU-only rendering. WebGL support not detected." and menu/game screenshots had no Flutter-rendered PNG art. A bounded verifier change removing --disable-gpu and adding --enable-webgl, --ignore-gpu-blocklist, and --enable-unsafe-swiftshader produced the same game at 390x844 with stage, jester, symbols, 0 console errors, and a balance-changing spin. This is a verifier environment mismatch, not an asset-file failure.

    Measured result: before correction, screenshots were visually blank for Flutter Image.asset content; after correction, 7 viewport captures rendered art and the 20-tap soak ended with -5.0% heap growth and 0 new console errors.

    Proposed bounded remedy: update the shared web verifier Chrome launch flags so CanvasKit uses WebGL/SwiftShader in headless Chrome instead of forcing a CPU-only path that drops image layers. Preserve all runtime/error/soak gates.
